# 寻路 0.1.5:按组合拆开的设计稿

状态:用户 10-10 同意按本稿做,第六节三处取建议(甲、"不改地形能原路回到起点"、接受路线变化);从第 1 步开始。现行架构见 `pathing.md`(第四节分层、第六节事实归属),本稿只写 0.1.5 要动的地方。

原则(10-10 用户定):每个问题先问为什么出现、是不是结构有缺口,改在出问题的那一层,不在下游补;寻路的各部分按职责拆成
能单独测、靠组合拼起来的部件,每个判据只有一个出处。不再照搬 Baritone 的结构与常数。

**规划是执行的子集(10-10 用户定)**:规划说能走的,执行必须走得了;规划判不准的走法,宁可不考虑,也不能先承诺、到执行时再做不到。
执行可以比规划会的更多(比如临场多探一点身),但那不进规划。所以:

- 每种走法的前提只收有把握的情形,判据和执行用同一个函数、同一个身体位置;拿不准的边界一律判为不成立。
- 执行时出现"走不下去"(`Journal.blockages`)、"卡住"(`stuck`)、`NO_FACE` 这类结果,一律当成规划的前提错了(规划骗了人),修在前提里收紧,不在执行层加兜底。
- 靶场把它当不变量:完好地形上(不算被外力打断),每条路线的走不下去、卡住次数都应为 0;大于 0 就是一处要查的前提。
- 把握一点点长:执行会、规划还没把握的技巧,先在靶场里补专门的地形证明它稳(多遍、两个加载器都成),再把它的成立条件写进前提;
  靶场同时看两样——走不下去、卡住必须是 0(不骗人),到达率逐步上升(会得多)。

## 一、靶场看到了什么

靶场:`numen/pathing/src/gametest/terrain/hills`(种子 0、`r.0.0` 的固定存档),18 条路线,`-Pgametest=numen_pathing_terrain`。
基线(10-10,`83e8c05a6`):16 条到达、2 条失败;两个加载器各三次,逐条一致(只有 `basin_descent` 在 Fabric 上差 ±2 刻)。

| 现象 | 数据 |
|---|---|
| 上一格的估价偏低 | ASCEND 实际 2697 刻 / 估价 1552 刻 = **1.74**(真机日志量到 1.67);WALK 1.07、DIAGONAL 0.99、DESCEND 1.19 |
| 上下坡不疾跑 | 坡上走、上交替,几乎每一步都按走路速度 |
| 百格路线要切段 | uphill、downhill、long_a、long_b、ridge_detour 各预算用尽一次,basin_descent 三次;代码注释说"百格两三千到四千个节点" |
| 困在半腰 | `ravine_floor`:半程路线里连续 9 次计划内坠落,落到峡谷壁的平台上,四面无路(`NeedsChanges`) |
| 游不过去 | `long_300`:规划出的游泳那一步执行不了,三次重搜得出同一段,`OutOfBudget` |
| 结果随墙钟变 | `basin_descent`:接续段晚到,最后一步不知道下一步是什么,差 2 刻 |

## 二、病根:现在哪些事实散在几处

### 1. 身体怎么动,有三份物理

| 出处 | 管什么 | 问题 |
|---|---|---|
| `plan/ActionCosts` | 走、跑、潜行、水里、攀爬的速度常数;按原版重力逐刻算下落;`JUMP_ONE_BLOCK` | 常数写死原版玩家,不读身体属性(速度、起跳力度、重力);`JUMP_ONE_BLOCK = fall(1.25) − fall(0.25) ≈ 3.2 刻` 是"升到一格高"的时间,不是"落在高一格上"的时间——照原版逐刻推,起跳到落在 +1 上要 **9 刻**(顶点 1.252) |
| `world/BodyStats.jumpHeight` | 按身体的起跳力度与重力逐刻积分出跳多高 | 只用来判"跳不跳得上",不给代价用 |
| `drive/Steering` | 地面加速度、摩擦、空中加速度、还有几刻落地,用来预判按前进还是后退 | 执行层自己的一份,和上面两份互不相识 |

上一格的估价错,估价(启发)也跟着错:`ESTIMATE_UP = JUMP_ONE_BLOCK`,往上每格只估 3.2 刻,真实最少 8.5(爬梯子)到 9(跳)。
估价越松,A* 展开越多——"百格路线展开过一万"多半是这个,`Driver.HAND_OVER` 注释里的依据跟着失效。

### 2. 能不能疾跑,在两层五处定

- 规划:`Walk`、`Diagonal` 各自按"不起跳、不改地形、不涉水"定 `sprint`;`Ascend`、`Drop` 写死 `false`;`Parkour` 另有一套。
- 执行:`SprintPolicy` 再加"下一步也得能跑";`Control.flows` 决定这一步走完停不停。

疾跑本是一段连贯动作的性质(冲劲跨步保持),现在被拆成每步一个开关,再用"下一步也得能跑"补连贯——坡上走、上交替,整段都跑不起来。

### 3. 段状态机一个类管了七件事

`drive/Driver`(736 行):认步、派发与接续、半程策略(`HAND_OVER`、`STALE_PARTIALS`)、走不下去的重搜(`STRIKES`)、
到达、收场、下载具,外加日志与记账。几条策略常数写在类里,改一条就得读懂整个状态机;单测只能连着整个 `Driver` 测。

### 4. 半程路线对不可逆的动作没有约束

搜索预算用尽时交出"离目标最近"的那一截,不管这一截里有没有回不了头的动作(落差超过能爬回去的坠落、往下挖穿)。
身体照着走下去,走到这一截的终点才发现下面接不上——`ravine_floor` 就是这样困在半腰的。

### 5. 执行受墙钟影响

- `Step` 在开始的那一刻抓住"下一步"(`after`);接续段如果在这之后才到,这一步仍当成"后面没有路",收住脚步。
- 提前搜下一段的时机(`lookahead`)按剩下几步的**估价**算"还剩多少刻",估价偏低,就派得偏晚。

两条叠在一起,同一条路线跑出来的刻数取决于搜索线程快慢——靶场里的 ±2 刻就是它。

### 6. 游泳的规划与执行对不上

规划认为那一步游得过去,执行做不到,重搜得出同一段。归 0.1.5 的"征服水"一起做,本稿不展开。

## 三、目标:部件与组合

```

                         │ Navigator · Report(含 Journal)   │
                         └───────┬───────────────────┬───────┘
                   规划查询       │                   │  执行
        ┌────────────────────────▼──┐        ┌───────▼─────────────────────────────┐
        │ 搜索 search/               │        │ 执行 drive/                          │
        │  A* · 目标族 · 估价(取下界)│        │  Driver(只做组装) =                 │
        │  交出策略 HandOver(新拆出)│◄──────►│   认步 Tracker · 接续 Continuation   │
        └──────────┬────────────────┘        │   复原 Recovery · 到达 Arrival       │
                   │                          │  步态 Gait(新,疾跑只在这里定)       │
        ┌──────────▼────────────────┐        │  控制器(每种走法一个)· 看护 Watchdog │
        │ 规划 plan/                 │        └───────┬─────────────────────────────┘
        │  走法目录:前提 → Maneuver  │                │
        │  代价 CostModel = 运动学 + │                │
        │   规格罚分 + 许可 + 危险    │                │
        └──────────┬────────────────┘                │
                   └──────────────┬──────────────────┘
                     ┌────────────▼──────────────┐
                     │ 地形与身体 world/          │
                     │  落脚 · 净空 · 迈步 · 语义 │
                     │  运动学 Kinematics(新)    │
                     └───────────────────────────┘
```

### 1. 运动学 `world/Kinematics`(新)

身体怎么动只在这里算一份,读 `BodyStats` 与身体快照里的属性(移动速度、起跳力度、重力、脚下方块的步速与起跳系数),
照原版逐刻推,不写死原版玩家的常数:

- 水平:走、疾跑、潜行、水里的稳态速度,起步加速与停下的距离;
- 竖直:起跳顶点、落在 Δy 上要几刻、自由下落 N 格要几刻;
- 由此推出每种走法几何上的最短耗时(上一格、下一级、下落 N 格、跑酷跨距)。

谁读它:代价(价钱)、估价(取各种走法里的最小值,保证是下界)、`Steering`(预判落点)、`Watchdog`(期限的基数)。
`ActionCosts` 只留下不是物理量的权衡(摔伤折价、危险、要问许可的倍数、视线遮挡)。单测直接对照原版逐刻的数。

### 2. 走法目录 `plan/Moves` 与 `Maneuver`

只回答"这样走成不成立、要改哪些格、落在哪"。`Maneuver` 记事实(跳不跳、改哪些格、涉不涉水、落点、回不回得了头),
**不再记 `sprint`**:能不能跑交给步态与运动学。新增一项事实 `reversible`:不改地形能不能原路回到起点(落差在跳得上、爬得上的范围内),
由运动学判,规划、交出策略、诊断都读这一个。

### 3. 代价 `plan/CostModel`

价钱 = 运动学给的耗时 + 规格的罚分 + 改地形(许可、料、挖多久)+ 危险。组合方式不变,只是耗时全部来自运动学。

### 4. 步态 `drive/Gait`(新)

拿到一段路线,一次算出每一步怎么走:跑不跑、要不要带着冲劲进下一步、在哪一步收脚。判据只看路线本身的事实
(方向连不连贯、下一步要不要原地改地形、落点接不接得住冲劲),**疾跑、收脚全模块只在这里定**,控制器只照做。
`SprintPolicy`、`Control.flows`、各走法里的 `sprint` 字段并进来后删掉。

### 5. 交出策略 `search/HandOver`(从 `Driver`、`Search` 里拆出)

什么时候先交一截半程路线、交哪一截,只在这里定:

- 交出的那一截**只能停在最后一个"回得了头"的节点上**:截里含不可逆的一步,就往回截到它之前;没有可交的(第一步就不可逆),
  就继续搜到目标或搜完,不交半程。
- 交出的节点数阈值不再拍定:运动学修好估价后,按靶场量到的展开节点数重定,写进注释的依据要和数据对得上。

### 6. 段状态机拆开

`Driver` 只做组装,四件事各一个部件,各自能单测:

| 部件 | 管什么 |
|---|---|
| 认步 `Tracker` | 身体此刻在哪一步(往前认、往后退、离开路线) |
| 接续 `Continuation` | 何时提前搜下一段、怎么拼;按运动学估的剩余时间派,不用估价 |
| 复原 `Recovery` | 走不下去几次重搜、半程路线不再变近就收场;常数随它走 |
| 到达 `Arrival` | 停稳、只看目标自己的判定、视线复核 |

**确定性规则**:身体只在"后面接什么"已经定下来之后,才开始执行路线末尾那几步(步态算出的收脚距离之内)。
接续段先到就带着冲劲接上,后到就按"后面没有路"收脚——两种情况都由路线数据决定,不由线程快慢决定。

### 7. 看护与报告

`Watchdog` 的期限以运动学给的最短耗时为基数,`Journal` 不变,另加每次搜索展开的节点数(验证第 5 条的依据)。

## 四、分步落地

每一步都单独提交、单独验:单测、日常 570 条(两个加载器)、靶场 18 条连跑三次一致,并和上一步的基线逐列比。
代价一变,路线会变,所以每步都重量基线,变化要能用这一步的改动解释。

| 步 | 做什么 | 预期靶场变化 |
|---|---|---|
| 1 | 抽出 `Kinematics`,单测对照原版逐刻;代价、`Steering`、`Watchdog` 改读它;`ActionCosts` 只剩权衡 | ASCEND 实际/估价从 1.74 回到 1 附近;路线可能改走少爬坡的;刻数可能略升(估价准了不等于走得快) |
| 2 | 估价改用运动学下界;`Journal` 加展开节点数;按数据重定交出阈值 | 百格路线的展开节点明显下降,预算用尽次数下降 |
| 3 | `Gait` 统一疾跑与收脚,删掉五处旧判据 | 坡上的平均速度上升,总刻数下降 |
| 4 | 拆出 `HandOver`,加"只交回得了头的一截" | `ravine_floor` 不再困在半腰:要么找到路,要么在起点就交出 `NeedsChanges` |
| 5 | 拆 `Driver`,加确定性规则;接续按运动学估剩余时间 | 两个加载器、三次运行逐刻一致(`basin_descent` 的 ±2 刻消失) |
| 6 | 游泳这一步不骗人(窄范围,已完成) | `long_300` 的游泳卡住 3 次降为 0;另加 `lake_cross`、`lake_shallows` 两条游泳路线当以后"征服水"的基线 |

**顺序调整(10-10)**:第 1 步做完后,`basin_descent` 六遍里出现 1716 与 1398 两种结果(派搜索那一刻的身体位置随线程快慢变,
两条总价几乎相同的路线轮流被选中)。靶场是衡量每一步的尺子,尺子本身不稳就没法判断后面的改动,所以第 5 步(拆 `Driver`、确定性规则)提到第 2 步之前做。
之后的顺序:5 → 2 → 3 → 4 → 6。

**待定(第 5 步发现)**:`basin_descent` 的非确定性实际来自靶场——搜索快照只拷"已加载"的区块,区域边缘的区块随墙钟加载。
靶场已改成开跑前整片阻塞加载。真机上同样存在:搜索对"没加载的区块"按什么口径算(当墙、当未知、等加载),现在由加载进度决定。
按"规划是执行的子集",没加载的格不被规划当成能走:一步的前提读到了没加载的列就不走这一步,停因记成"未加载"(`SearchTest.theSearchStopsAtTheEdgeOfTheLoadedChunks`、`SnapshotAndDispatchTest` 钉着);没到目标时交的半程由 `HandOver` 截在回得了头的节点上(`HandOverTest`),身体走过去、区块加载了从那里接着搜。第 4 步定的口径,没有新增规则。

**待定(第 2 步发现)**:
- 攀着(梯子、藤蔓、脚手架)时不按键会下滑:已定"攀着不算挖放工位"。段状态机等接续时的位置第 3 步定了:等在待得住的节点上(`Continuation.settled` 把等的位置从末尾几步往前退,退到起点不是攀着的那一步),不用"保持动作"——潜行只托得住梯子、藤蔓,脚手架上蹲着反而往下穿,没有通用的保持办法。路线一开头就攀着(从梯子上重搜)时没处可退,只能在那儿等搜索,滑的是搜索那一两刻。
- 脚手架顶板对潜行的身体让开:潜行探出搭桥已按蹲着的身体判;别的走法若在脚手架上潜行,同样要问一次蹲着的碰撞。
- `build.lua` 的原地打转判据计入已放下的格数后,两格互相带掉的无限乒乓只靠脚本调用上限收场。
- `fish_reels_in_from_a_pool` 偶发(分支约 1/21、基线 0/8,分不出来),与寻路无关的可能大,未查。

**待定(第 3 步发现)**:
- 步态判"带不带冲劲进下一步"用 `Kinematics.stopDistance` 对 `Stepping.slideRoom`,直角转弯 0.208 对整块余量约 0.2,差得很薄;"晚一刻反应"与 0.05 步长是沿用取值,没有实测。速度不同的身体可能翻转——靶场加一块窄台阶、急弯多的地形专门量,再定余量。
- 路线一开头就攀着(从梯子上重搜)时没有待得住的节点可退,只能在梯子上等,搜索那一两刻会滑。

**待定(第 4 步发现)**:
- `ravine_floor` 现在不再走进峡谷(半程都截在崖沿上回得了头的节点),但结局是 `OutOfBudget`(崖沿一大片,一万个节点搜不完),不是更有用的 `NeedsChanges`。
  以前说得出 `NeedsChanges`,是因为她已困在半腰、能走到的范围小、搜得完。要在起点就说清"不改地形到不了",
  得让诊断在半程停滞时,在不交半程、只算"不改地形能走到哪"的条件下把可达范围搜完(或按区块范围给出确定上限)再下结论——归诊断,单独一步。
- 出水按岸沿高出水面不超过 0.6 格判(读自原版 `LivingEntity.travel`,未实测),0.6–1 格之间偏保守地判回不去;跑酷恒判回得了头,没为反向的跳单独算。

**第 6 步(游泳这一步不骗人)已完成,范围只到这一步**:`long_300` 里三次游泳卡住是同一件事——游进深水里夹着的一格深浅滩时,规划里落点是踩在水底上
(`Stance.GROUND`),`SwimControl` 却按住跳把身子托在水底之上老远(原版水里不按键每刻只沉 0.005 格),段状态机等脚着地等不到。
修在 `SwimControl`:落点是站着的,到了落点那一列的中心就按住潜行沉下去(规划没错,执行没照它做)。`FluidGameTests.swims_from_deep_water_onto_a_shallow_bed` 与
`MovesTest.swimmingFromDeepWaterOntoAShallowBedLandsStandingOnTheBed` 钉着。

留给"征服水"的问题(只列,不做):
- 估价在水里偏低约三倍(估价按疾跑 3.56 刻一格,水里一格 10.2 刻),横渡一道湖要展开十几万个节点、十几段半程(`long_300` 12 段、11 万节点)。
- 水里只有四个正方向与上下,没有斜着游;原版疾跑游泳(游泳姿势,身子只剩 0.6 高)比水里走快得多,规划与执行都没用上。
- 浅水里"浮着"和"踩水底"是两种姿势,规划里按水底有没有托着脚定,执行在水里走(`wading` 的平走)不按跳,会浮在水底之上多久、算不算到,没有逐种地形验证过。
- 流水、气泡柱、岸沿高度在 0.6 到 1 格之间的出水、水下作业与憋气的衔接、船与水桶,都没有进规划的前提。

## 第 7 步:给模型的寻路瘦身(10-11 与用户定,已落地)

**起因**:真机里主人开观察模式钻进地下,她跟下去试了五次。日志里每次失败都不是权限层拦的(出厂行放行挖自然方块),是另外两道关:
`costs = {dig, place}` 默认不许改地形,许了以后 `move.go` 又守"只改计划里列出的格",而计划只看清一截,剩下要挖的格必然不在计划里。
"能不能动这一格"在三处判(`costs`、计划承诺、权限层),前两处是工具里的"我可以吗",违反"改世界的动作只由权限层决定"。

**口径**:模型只说去哪、多近算到;怎么走归寻路,能不能动归权限层,够不够得着归动手的工具。参照 mineflayer-pathfinder
(每次只给 Goal,走法是整只机器人的配置,默认可挖)与 Mindcraft(给模型的 `goToPosition(x,y,z,min_distance)`,挖、放离得远自己先走过去)。

| 给模型的 | 说明 |
|---|---|
| `numen.move.to(目标, 距离?)` | 唯一的"去一处"。目标照旧:Pos、方块、实体、团、Cells、一列 `{x,z}`、一个高度 `{y}`。距离缺省:能站进去的格就站进去,站不进去的方块与实体走到旁边。后台任务:规划一截、走一截、按同一份规格接着规划,到了或真到不了才收 |
| `numen.move.away(某物, 距离)` | 离开某物至少多远 |
| `numen.move.follow(谁, 距离?, 秒?)` | 与 `to` 同一套走法,同样可挖可放 |
| `numen.use.dismount()` | 下载具是一下潜行,和上载具(`use.entity`)同属 `use`;`move` 不上不下 |
| `numen.move.explore`(库) | 内部改用 `move.to` |

删掉:`numen.route` 整组、`numen.move.go`、计划对象与它的存取、`numen.move.flee`、描述表里除去处与距离以外的全部
(`arrive`、`stops`、`mode`、`costs` 全部旋钮、`avoid`/`avoid_break`/`avoid_place`/`avoid_step`、`allow`、`materials`)。

- **可挖可搭,只看价钱**:能走就不挖,绕太远才挖;垫路料按出厂的 `numen:throwaway`。许不许全由权限层:禁止的格是墙,要问的格加价(倍数照旧),
  走到跟前那一刻问;拒了那一格在这一趟里当墙、重新规划绕开,绕不开才以 `denied` 收场。观察模式下权限层拒一切改动,她自然只走。
- **不再有"计划承诺"**:每一截规划仍是执行的子集(前六步的规矩不变),截与截之间按同一份规格从她当时的位置接着搜,不比对"是不是计划里列过的格"。
- **载具只是规划的输入**:规划读她当时的状态,坐在船上就按划船规划(开到离目标最近的水面,岸上的目标停在岸边、仍坐着、照实交回);坐着驾驭不了的东西当场拒绝并指 `numen.use.dismount()`。
  走路的一趟从不自己下车。用不用船归"征服水"。
- **动手的工具自己走过去**:够不够得着是动作的前提,判据只在动作那一处(寻路的 Use/Dig/Place 到达目标)。`InReachTask` 系的单目标动作
  (`use.block`、`use.entity`、`use.hit`)、`work.dig`、`build.place` 够不着时先走到够得着处再动手;多格的按"走到够得着剩下最多格的地方、做完够得着的、再走"
  循环到做完或真到不了。`build.diff` 只读,不走。09-30 "动作不走路、走路是脚本的一步"的设计由此改掉。
- **知情权**:`move.to`/`away`/`follow` 与会走路的动作,回执照实交代这一路:停在哪、离目标还差多远、挖了几格放了几格、问过什么、被拒了什么、没到的原因。
  这份路程回执只有一个类型,各处共用。
- **物理安全留在寻路**:不挖脚下那格、头顶的沙砾、挖开会放出流体的格、摔落高度按血量,不属权限层。

**验**:靶场加了地下目标的两条路线(`buried_cell` 从地面到封闭石头里的一格,`buried_cavity` 到开跑前挖出的一间 3×3×3 空房),模块的靶场
走路规格改成可挖可搭;日常批两个加载器、tlm 全过。往下挖时估价只能按"可能有洞直接掉下去"取下界,展开会多,没有为它加不可采纳的估价。
老路线里 `basin_descent` 在可挖可搭后搜索展开翻了几倍、预算用完没走到(原来 1088 刻到达),是这一步的已知代价,留给后面的估价与预算。

**靶场回归的根因与取舍(10-11 查清)**:代价模型没有对挖掘说谎——各走法实际/估价在 1.0 到 1.2 之间,挖着走的步也不偏低;不交半程、一次搜到底时,
`hill_detour` 13007 个节点、473 刻到(基线 677,穿山两次挖比绕路便宜),`ravine_cross` 15975 个节点、465 刻(与基线同一条路),`basin_descent`
132656 个节点、1052 刻到(基线 1088)。回归来自两件事叠在一起:
- 往下的估价只能按"可能有洞直接掉下去"取下界,默认可挖后 f 等值面内每个地面节点都长出往下挖的分支(`basin_descent` 一次搜到底的展开里 `DOWNWARD`
  占 58%,水平走法的展开数与不挖时相同),节点数翻几倍(`ravine_cross` 6606→15975,`basin_descent` 46175→132656);
- 每段展开到 `HandOver.NODES` 一万个就先交半程,而挑半程的几档折算(`AStar.COEFFICIENTS`)最后几档只看估价,交出去的是估价上近、真实代价上贵的节点,
  身体被带进完整搜索不会选的路(`hill_detour` 实走 1586 刻,中间一段含三次挖、单段价 585);`basin_descent` 的半程落进死胡同,下一段每次四万个节点的预算内
  搜不完,收场 `OutOfBudget`。

试过的半程挑法(靶场逐条跑,数据在 10-11 的会话记录):纯 f 最小的前沿——`uphill`、`lake_cross`、`lake_shallows`、`buried_cavity`、`basin_descent` 都没走到
(估价按疾跑、与真实代价差三成以上时,f 最小的前沿是最浅的节点,不是最优路线的前缀,`Recovery.stalled` 随后判停滞);focal 式(f 不超过最小 f 的
(1+ε) 倍的前沿里取估价最小的)——ε 取 0.15 到 2.0 靶场结果相同、`hill_detour` 508 刻、`buried_cavity`/`uphill`/`lake` 都到,但 `basin_descent` 仍没到,
而且 `WalkGameTests.a_far_walk_that_changes_nothing_walks_all_the_way`(平地走 208 格)在 ε 取 0.01 到 0.5 都失败:平地上 f 等值面里最靠近目标的节点是"多挖几格、
更早到"的那些(估价偏低,走得越远 g 与 h 的差越大),挑出来的半程带着挖(挖 15 放 1),ε 取 0.01 时甚至走不到。所以没有采用,半程挑选保持原样。

**已知回归(留给估价这一层,征服水之后做)**:`basin_descent` 没走到;`hill_detour` 1586 刻(基线 677)、`ravine_cross` 512 刻(基线 465)比基线慢。根因都在估价:
默认可挖后往下的估价只能按掉落取下界,f 等值面里每个地面节点都长出往下挖的分支,一次搜到底十几万个节点,半程落进死胡同后下一段预算内搜不完。修法归估价这一层,
不放宽估价、不调预算;候选:同一趟内记住死胡同、修正估价的 LRTA* 式学习,或粗层抽象估价/地标。

## 第 8 步:估价这一层(10-11 规划,先量后改)

**为什么是它**:第 7 步的三条已知回归、水里的估价偏低三倍(`long_300` 十一万节点、`lake_cross` 两万)、半程挑法换不动(纯 f 最小、focal 都失败),
根都在同一处——估价离真实代价太远,f 等值面太宽。搜索、半程、预算都不动,只把估价做紧,前提照旧是**不多估**(A* 仍找最优)。

**现状**:估价 = `Pace.estimate`(水平按疾跑走八方向距离、竖直上按爬、下按自由落体,取大者)+ `Burial.floor`(从终点往外做一次放宽问题的 Dijkstra,
只数路上至少要清开的实心格,已经是"放宽问题的精确解"式的估价)。缺口按地形分三类:往下(只能按"可能有洞"取掉落)、水里(按疾跑估,真实约三倍)、
平地(疾跑 3.56 刻对实际约 4.4 刻,差三成:起步加速、转向、收脚)。

**先量**(派执行者做一次诊断,不改行为):靶场每条路线一次搜到底拿到最优路线,沿路每个节点比"估价 / 真实剩余代价",按地形(平地、上坡、往下、水里、挖)
分摊差距从哪来;再数半程落进死胡同时,第二段在多大范围里重复展开。产出一张"差距来源"表。

**再改**,候选按改动由小到大,由数据挑:
1. **同一趟内边走边学**(实时启发式搜索的 RTAA* 规则):每段搜完,已展开的节点把估价抬到"开放集里最小的 f 减去它的 g",存在这一趟的表里,下一段
   估价取它与原估价的大者。照这条规则抬过的估价仍不多估;死胡同那一片被抬高,下一段不再往里钻。只在这一趟、这一个目标里有效;地形变了(不是
   她计划里的改动)那一段的学到的值作废。对症 `basin_descent` 第二段的重复展开。
2. **把 `Burial` 的放宽问题做全**:放宽问题里不只数要清开的格,也算挪动的下界——摔落有高度上限(规格的 `fall`),往下穿过空气每落那么高至少要有一处
   落脚;水里每格按水里最快的游法计。仍是放宽问题的精确解,仍不多估。对症往下与水里。
3. **粗层估价**(区块段之间的口子,脏了只重算那一块):在 1、2 不够时再上,和"分层寻路"一起评估。

**验收**:三条已知回归回到基线或更好(`basin_descent` 到达);`WalkGameTests.a_far_walk_that_changes_nothing_walks_all_the_way` 等平地不多挖;
水路三条的展开数明显下降;其余路线不变坏;每段搜索的耗时(估价本身也要钱)记进 `Journal` 一起比。估价变紧之后,再回头看半程挑法是否值得换。

## 五、验收

- 靶场:到达率、总刻数、各走法实际/估价(都应接近 1)、每次搜索的展开节点、半程次数;两个加载器各三次逐刻一致。
- 日常 570 条、tlm 15 条、单测全过;寻路单测里每个新部件都有自己的测试,不经 `Driver`。
- 每个新部件的判据在 `pathing.md` 第六节"事实归属"里登记一行,旧的出处删掉。

## 六、要用户定的选择

1. **A* 里疾跑怎么计价。** 搜索按单步定价,看不到"这一步在不在一段连贯的跑动里"。
   - 甲(建议):每一步按它物理上能达到的最快步态计价,步态部件只要能跑就跑;两者只在起步、收脚处有偏差,靶场量出来看有多大。
   - 乙:把"进入这一步时的速度"放进搜索节点的状态。准,但状态空间翻几倍,搜索变慢。
2. **"回得了头"怎么定。** 建议:不改地形能原路回到起点(落差不超过跳得上、爬得上的高度)。往下挖穿、跳进水里但游得回来的算不算,按运动学判。
3. **第 1 步会改变路线。** 估价变准后,寻路会更少选爬坡多的路,真机上可能看起来"更爱绕"。这是对的方向,但会和现在的观感不同。
