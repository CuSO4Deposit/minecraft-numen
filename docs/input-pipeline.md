# 输入管线:渠道、收件箱、大脑、身体

状态:方案(2026-10-11),0.1.5 不做,0.1.5 主线是寻路。

**定下来的方向**(10-11 用户拍板):服务端必装,客户端可选,外接大脑放在服务端。理由:外接大脑现在挂在主人的客户端上,
主人一下线就没人能操控她。放到服务端,她才是"你在 Minecraft 里的个人 agent"——你不在线,她也能听你从别处说话、替你干活。

## 一、现在是什么样

```
主人客户端                                         服务端
┌──────────────────────────────────────────┐      ┌───────────────────────────────┐
│ 输入:面板、快捷对话、插件桥接(弹幕、群消息)│      │ 身体与任务                     │
│   → 收件箱 EventQueue(落盘在客户端)        │◄─────│ NumenEvents.emit(主人离线进出箱)│
│ 循环 AgentLoop + 模型调用(主人的 key)      │      │                               │
│ 对话、札记、待办、人设、技能、模块真源       │ ───► │ ServerPrograms 执行 Lua         │
│ 外接大脑 McpServer(本机端口)              │      │ 权限层、寻路                    │
└──────────────────────────────────────────┘      └───────────────────────────────┘
```

10-05 定的"客户端想、服务端做"把 Lua 程序搬到了服务端,手脚已经在服务端。剩下全在主人客户端:收件箱、循环、她的记忆、外接大脑。
所以主人一下线,她的身体还能把手上的活干完,但听不见、想不了。

## 二、目标:三层两管

```
渠道(谁在跟她说话)        大脑(谁替她想)              身体(她做事)
游戏聊天 @她 ─┐                                         
面板、快捷对话 ┤                ┌─ 主人客户端代调模型 ─┐
/numen 命令 ──┼─► 收件箱 ──► 循环 ┤                     ├─► Lua 程序 ─► 身体、任务
QQ、Discord ──┤  (每只一个)      └─ 服务端直调模型 ────┘    (ServerPrograms)
弹幕、定时 ───┤        │                                         │
世界的事 ─────┘        └──────── 外接大脑(远程 MCP)取件、发程序 ──┘
```

- **收件箱、循环、她的记忆都在服务端,跟着她的身体。** 收件箱是她的,不是哪个大脑的。
- **大脑是可以换的。** 同一时刻只有一个在驾驶,现有的"驾驶席"(`McpMode.driving()`)推广成三选一。
- **渠道只管把话送进收件箱、把她的回话送回去。** 加一个渠道不碰大脑,换一个大脑不碰渠道。
- **客户端只做两件服务端做不了的事**:用主人自己的 key 代调模型(key 不出主人的电脑),以及呈现(面板、打字机、语音、look 的渲染)。

单人游戏是同一个进程里的内置服务端,路径完全一样,不多一跳网络。

## 三、收件箱搬到服务端

`EventQueue`、`EventTypes`、`JsonlJournal` 本来就在纯 Java 的 `agent` 模块里,不碰游戏类,可以原样搬。

- **每只同伴一个,落盘在服务端**,跟着这只同伴的存档,入队即落盘、取走即清,与现在同一套规则。
- **入口只有一个。** 服务端 `NumenEvents.emit`(世界的事)和客户端 `NumenGateway.emit`(主人的话、桥接)合成服务端的一个入口。
  客户端上的输入经网络包送进来,不另开一条路。
- **出箱(`EventOutbox`)删掉。** 它存在是因为收件箱在客户端,主人离线时事件没处放;收件箱在服务端,离线就只是"攒着"。
- 每个条目记**从哪个渠道来**(游戏聊天、面板、QQ……)与**谁说的**(群聊已经按人记)。她回话时按这个送回去(§六)。

## 四、循环搬到服务端,模型调用可以在任何一边

循环内核 `AgentLoop` 也在纯 Java 的 `agent` 模块里,对外只靠端口(`ModelPort`、`ToolPort`、`Transcript`、`Inbox`)。搬到服务端以后,
"大脑在哪"只剩一个问题:**模型由谁来调**。这正好是 `ModelPort` 的两种实现,加上一种不走循环的:

| 大脑 | 怎么跑 | key 在哪 | 什么时候用 |
|---|---|---|---|
| 主人客户端代调 | 服务端把请求发给主人的客户端,客户端用主人的 key 调模型,流式回传 | 主人的电脑,永不上传 | 主人在线、装了客户端。现在的默认就是这个,只是循环换了位置 |
| 服务端直调 | 服务端自己调模型 | 服主的配置 | 服主开了、给了配额;主人下线后接班 |
| 外接大脑 | 循环停牌,远程 MCP 驾驶(§七) | 外接 agent 自己的 | 主人用自己的 Claude Code、Codex 一类 agent 指挥她 |

- **代调走现有的反向请求。** 10-05 的程序宿主已经有"服务端反向问客户端"的机制(带超时、程序收尾撤销),代调模型是它的一种请求。
  请求体是一轮的上下文(几万 token,百来 KB),配上已有的载荷分片。
- **呈现订阅循环事件。** 打字机、语音、气泡、token 台账现在订阅 `LoopEvent`;循环在服务端以后,事件经网络包推给在线的主人客户端,
  订阅者不变。没装客户端时只剩气泡与聊天行(服务端就能做)。
- **主人下线怎么接班**,由主人给每只同伴选一项:停下待命(默认)、服务端大脑接班(服主允许时)、外接大脑接班。
  主人上线时交还给他选的大脑。驾驶席只在一处判。

## 五、她的记忆存在哪

**要和你定的第一件事。** 10-05 的口径是"服务端不存任何大脑数据"。现在大脑可以换,换了以后她还得记得自己干过什么,
所以她的记忆必须有一份在服务端。建议这样分:

| 数据 | 存哪 | 理由 |
|---|---|---|
| 收件箱、对话历史、札记、待办、长期目标 | 服务端,跟着这只同伴 | 这是她在这个世界里的经历。换哪个大脑都要读到同一份,夜里服务端大脑做了什么,早上你上线她还记得 |
| 人设 | 服务端,跟着这只同伴 | 同上。主人在面板上改,改的是服务端那一份 |
| 模块与技能(她的手艺) | 主人客户端是你的个人库;服务端存一份她在这里用的副本 | 手艺要能带去别的世界。主人在线时照现在的哈希缓存同步上去,副本落盘;主人不在时离线大脑用副本 |
| 模型服务商与 key | 哪个大脑调模型,就在哪一边 | key 不跟着数据走 |

**照实说代价:** 服主看得到她的对话与札记。她的身体本来就在服主的机器上,这一点和在服务器上盖房子一样;单机没有这个问题。
主人可以在面板上一键导出、清空她的记忆。

## 六、渠道

| 渠道 | 怎么进 | 她的回话送到哪 |
|---|---|---|
| 游戏聊天 | 主人在聊天栏 @她,或私聊她 | 聊天行、头顶气泡 |
| 面板、快捷对话(要客户端) | 网络包 | 面板、打字机、语音 |
| `/numen` 命令 | 服务端命令 | 命令回显 |
| QQ、Discord、弹幕(远程) | 远程端点,持"渠道令牌"(§七) | 原渠道,也照常在游戏里说 |
| 定时、世界的事 | 服务端自己 | 不需要回话 |

- **她说的话总在游戏里说出来**(气泡、聊天行),另外送回问她的那个渠道。从 QQ 问的,QQ 上收到回答。
- **没装客户端也能用。** 说话靠聊天 @她;征询卡变成一条带可点按钮的聊天消息(底层就是现有的 `/numen consent`);
  她在干什么用动作栏或 Boss 栏显示;1.21.6 起可以用原版的服务端对话框做更像样的卡片。面板、语音、look 的渲染需要客户端。

## 七、远程端点:外接大脑与远程渠道共用一个口

现在的 `McpServer` 挂在主人客户端(`numen-api/common/src/client/.../mcp/server`),本机端口、一个令牌。搬到服务端后,一个服务器一个端点,所有人共用:

- **按令牌认人。** 主人用 `/numen token` 发令牌,可随时作废;存档里只存令牌的哈希。照 MCP 的授权规范做。
- **令牌带作用域**:
  - 能指挥哪几只同伴(只能是自己名下的);
  - 角色:**大脑**(取件、发程序、说话,等于驾驶)或**渠道**(只能把话送进收件箱、收她的回话)。QQ 机器人拿渠道令牌,
    Claude Code 拿大脑令牌。
- **权限不会因令牌变大。** 外接大脑发的程序和内置大脑一样过权限层,主体是那只同伴;令牌给不出主人自己都没有的权限。
- **限流**:每个令牌限并发与频率,服主可配总量。
- **协议**:Streamable HTTP,多会话;工具与现在相同(`lua`、`skill`、`todo`、`memory`、`get_events`、`say`)。
- **端口**:先做"服主自己开端口,建议套反向代理加 HTTPS";再调研"和 MC 共用一个端口,按开头几个字节分流"。中继服务等用的人多了再说。
  这和"不开自己的端口"的旧定论冲突,冲突的原因是那条定论只考虑了客户端。

## 八、以后:夺舍

主人下线时,用和主人同一个身份的假玩家顶替主人的身体干活(像 Carpet 的 `/player shadow`)。在本方案里这只是"换一个身体来源",
渠道、收件箱、大脑都不变。要单独定:上线时的交接(防复制物品)、主人明确授权与范围、死亡与危险保护、服主开关、回来时完整交代做了什么。
本方案不做。

## 九、分步落地(0.1.5 之后)

每一步单人游戏行为不变,日常 GameTest 两个加载器全过。

1. **收件箱搬服务端。** 入口合一、出箱删掉、条目带渠道与说话人;客户端面板经同步包读。
2. **循环搬服务端。** `ModelPort` 的"主人客户端代调"实现走反向请求;呈现订阅经网络包;驾驶席三选一。
3. **记忆搬服务端。** 对话、札记、待办、目标、人设落在同伴的存档;模块与技能的副本落盘;面板导出与清空。旧的客户端数据首次上线时迁上去。
4. **远程端点。** `McpServer` 搬服务端;令牌、作用域、限流、多会话;外接大脑与渠道令牌。
5. **无客户端交互。** 聊天 @她、可点的征询消息、动作栏状态、1.21.6+ 对话框。
6. **服务端大脑。** 服主配置服务商与 key、按玩家配额;主人下线后的接班选项。

## 十、要你定的

1. **她的记忆存服务端**(§五):经历与人设跟着同伴存服务端,手艺在你的客户端、服务端存副本。这会推翻 10-05 "服务端不存大脑数据"。
2. **循环搬服务端、客户端只代调模型**(§四),而不是客户端、服务端各跑一份循环。各跑一份就是两个循环、两份状态,换大脑时要对账,这正是要避免的多源。
3. **端口**先走"服主自开端口 + 反向代理"(§七)。
